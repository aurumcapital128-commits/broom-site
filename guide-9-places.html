01

~/.claude/projects — every agent session, kept forever

Claude Code saves a full transcript of every session, per project, and never expires them (issue #24207: no resource lifecycle management). Projects you abandoned months ago still hold every conversation. Transcripts are regenerable history — deleting old ones does not affect your code, your settings, or your agent's skills.

Check the damage
# Windows (PowerShell)
"{0:N1} GB" -f ((Get-ChildItem $env:USERPROFILE\.claude -Recurse -File -ErrorAction SilentlyContinue | Measure-Object Length -Sum).Sum/1GB)

# macOS / Linux
du -sh ~/.claude
Clean it safely (by hand)
# Look inside first. Each folder = one project's transcripts.
ls ~/.claude/projects
# Delete only folders of projects you no longer work on.
NEVER touch: settings.json, .credentials.json, CLAUDE.md, memory/, skills/, agents/, commands/, plugins/, hooks/ — that's configuration a human built. No cleanup is worth losing it.
02

~/.claude/file-history — the 300 GB folder

Every time the agent edits a file, the previous version is snapshotted here so edits can be reverted mid-session. It grows with every single edit, forever — the largest documented cases exceed 300 GB. Your real version control is git; this internal history is disposable once a session is over. The same goes for its smaller siblings shell-snapshots/, todos/ and debug/.

Clean it safely
# Close active Claude Code sessions first, then:
# Windows
Remove-Item "$env:USERPROFILE\.claude\file-history\*" -Recurse -Force
# macOS / Linux
rm -rf ~/.claude/file-history/*
03

ext4.vhdx — the disk that never shrinks

WSL2 and Docker Desktop store their entire Linux world inside a virtual disk file. It grows automatically when you add data — but never shrinks when you delete data. Free 40 GB inside Ubuntu and Windows still shows the same usage: the .vhdx stays as big as the biggest you've ever been. Storage Sense will never tell you this.

Find your virtual disks
# Windows (PowerShell) — lists every WSL/Docker vhdx with its size
Get-ChildItem "$env:LOCALAPPDATA\Packages","$env:LOCALAPPDATA\Docker" -Recurse -Filter *.vhdx -ErrorAction SilentlyContinue |
  Select-Object @{n='GB';e={[math]::Round($_.Length/1GB,1)}}, FullName
Compact one (the official way)
wsl --shutdown
diskpart
# inside diskpart:
select vdisk file="C:\Users\you\AppData\...\ext4.vhdx"
attach vdisk readonly
compact vdisk
detach vdisk
exit
CAREFUL: never delete a .vhdx — it IS your Linux system, not a cache. Compact only with WSL fully shut down. Docker Desktop has its own path: Settings → Resources → Disk usage, or clean inside Docker first (next section) so compaction has something to reclaim.

04

Docker — images, stopped containers, volumes, build cache

Docker keeps every image version you ever pulled, every stopped container, and every intermediate build layer. One command shows the truth, including the exact "reclaimable" column most people never see.

Check the damage
docker system df
Clean it safely — in this order
docker image prune -a      # images nothing uses (they re-pull when needed)
docker container prune     # stopped containers
docker builder prune       # build cache (next build is slower, that's all)
VOLUMES ARE DIFFERENT: docker volume prune can delete real data — the database of a project you merely stopped. Run docker volume ls and review each name before pruning. When in doubt, don't.
05

Orphaned node_modules — the classic, multiplied by agents

AI agents scaffold projects at a pace no human ever did — and abandon them the same way. Every abandoned experiment keeps its full dependency tree. On machines that run coding agents, 50–200 GB across dozens of forgotten node_modules is normal. If the project has a lockfile, one npm install rebuilds everything identically — deleting the folder loses nothing.

Find them
# The community standard (interactive, free):
npx npkill
# It lists every node_modules with size and last-use; delete with a keypress.
DON'T touch these two: your global npm root (npm root -g shows it — deleting it uninstalls your CLIs), and anything under a package manager's own cache (npm-cache/_npx). They look like orphans; they aren't. We learned this one the hard way.
06

Package manager caches — npm, pip, yarn

Download caches speed up installs. They also grow forever — multi-GB npm caches are routine on agent machines. Cleaning them breaks nothing: the next install simply downloads again. The one rule: always use each tool's official command — npm's cache is content-addressed and hand-deleting inside it corrupts the index.

Clean them safely
npm cache clean --force
pip cache purge
yarn cache clean
pnpm IS THE EXCEPTION: its store shares hardlinks with your live projects. "Cleaning" it can break installed node_modules. Leave pnpm's store alone unless you know exactly what pnpm store prune does.
07

Ollama models — ~/.ollama/models

Every model you ever pulled stays until you explicitly remove it, and Ollama doesn't track when you last used one. A single mid-size model is 4–8 GB; a year of experiments is easily 50+.

Check, then clean — official CLI only
ollama list
ollama rm llama3:latest    # re-pull any time with: ollama pull
NEVER delete blobs by hand: the files under ~/.ollama/models/blobs are indexed by hash and shared between models. Removing one manually leaves the index lying about what exists. ollama rm handles reference counting for you.
08

HuggingFace hub cache — ~/.cache/huggingface

Every from_pretrained() in every script you ever ran cached its full model here. It's pure cache — anything a script needs again re-downloads automatically — but it's often the single biggest folder on an ML machine. And if you also use Ollama or LM Studio, you may be storing the same model 2–3 times across tools.

Check, then clean — official tool
pip install -U "huggingface_hub[cli]"
huggingface-cli scan-cache          # shows every repo with size and last access
huggingface-cli delete-cache        # interactive: pick what goes
09

LM Studio models & desktop-agent VMs

LM Studio keeps models as plain files under ~/.lmstudio/models — easy to forget (on our own dev machine we found an 8 GB model untouched for over a year). And a newer, sneakier one: desktop AI apps that run sandboxed agents (Claude Desktop and friends) ship their own multi-GB virtual machines under AppData, invisible to every cleaner.

Check both
# LM Studio: one folder per model — delete a folder, delete a model. That's it.
# Windows
Get-ChildItem "$env:USERPROFILE\.lmstudio\models" -Recurse -Depth 2 | Select-Object FullName
# macOS
du -sh ~/.lmstudio/models/*/*

# Desktop-agent VMs (Windows; look, don't touch — uninstalling the app is the clean path)
Get-ChildItem "$env:LOCALAPPDATA\Packages" -Recurse -Filter *.vhdx -ErrorAction SilentlyContinue |
  Select-Object @{n='GB';e={[math]::Round($_.Length/1GB,1)}}, FullName
IN LM STUDIO, SKIP: credentials/, conversations/ and config folders — only models/ holds the gigabytes, and only models are safe to remove.
